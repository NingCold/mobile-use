# Known-path navigation

Use when local_navigation is reported and the authorized route is already known from inspected states or task instructions. Call navigate(observation_id,plan) instead of separate calls for every known page. A plan declares allowed_packages, 1..8 steps, timeout_seconds (at most 30), optional final settle_ms (0..2000) and until={text,package}. until uses the remaining plan budget and checks final readiness before delivering one observation; use it when the last page is known to load asynchronously. No scripts, loops, automatic input retries or coordinate taps are accepted. Missing targets and covering windows may wait within the step budget; ambiguity and detected dialogs stop immediately.

Each step has kind, package and timeout_seconds (default 5). For launch, package is the destination; no reset or force-stop occurs. For tap, package is the expected current app. Use target for an exact text/description/resource_id selector, optionally scoped by within_text, or visual_target for an authorized known visual action (below). Every structured target is resolved against fresh local trees, including visibility/covering checks. With tap_readiness, identity/context and target/ancestor geometry must remain sampled-quiet for 600ms by default, rather than merely agreeing twice. step.readiness={quiet_ms,timeout_seconds,busy?} can declare a 200..2000ms quiet window and an exposed busy/refresh control using an exact TargetSelector. While that control exists the quiet clock is reset; after it disappears or geometry moves, a full quiet window is required. The smaller of readiness and step budgets applies. Missing bound targets may return within the budget; changed context, ambiguity and covering layers still stop. Ordinary tap supports the same optional readiness object; omit it to retain its original one-shot structured validation. Readiness performs only local tree reads, with no intermediate delivery or screenshots. Use a real busy signal when exposed. With only geometry, a quiet window is a bounded fallback, not proof that a delayed refresh will never begin. No entire-page stability is required. Future targets need a known route, not invented labels. The initial observation authorizes the route from its inspected foreground, not stale IDs for later pages.

For swipe, supply swipe={start_x,start_y,end_x,end_y,kind,duration_ms}, using the original display dimensions of a known surface. kind is browse/fling. A page guard is mandatory: when.text (accessible substring, optionally with matching package) or visual_when={text,context_text,search_bounds?}. Visual guards are exact, unique labels from a known page, locally recognized and confirmed with a second image; they are not a semantic completion detector. An expected progress label may be declared only when the page's format is established. Use a sufficiently distinguishing condition. Unknown pages, missing progress, dialogs or new creatives require model inspection, not guessed guards or blind swipes.

Example of a known structured route: plan={allowed_packages:["org.example.reader"],steps:[{kind:"tap",package:"org.example.reader",target:{text:"Library"}},{kind:"tap",package:"org.example.reader",target:{text:"Open",within_text:"Report.pdf"}}]}. App-specific routes and labels belong to task documents/callers, not this skill or server defaults.

To continue immediately after existing bounded returns, put a plan in back_sequence.after, including tap.follow_up.return_back.after. Its packages must be a subset of the return boundary. The plan begins after the back keys; its timeout is separate from the existing timer budget. Supply the full plan up front: all parameter/dimension checks occur before the first input. The original display orientation must be restored before coordinate navigation. End the continuation before the next unknown target and inspect the final image there.

Only one final observation is delivered, including on recoverable failures. Inspect navigation.status, steps, wait.status when supplied, and each input_status; for a return continuation these are under continuation.navigation. A step may be sent even if its expected transition failed. sent/unknown steps must never be replayed as a sequence. Resolve a partial result from its returned state before planning further work. Timeouts bound local polling, not an in-flight device RPC. Neither final observation nor completed navigation proves business completion. Without until, the last tap can still be loading; inspect its delivered result.

## Known visual actions and immediate follow-up

A tap step accepts visual_target={text,context_text?,search_bounds?} instead of target, and requires when.text as a known accessible page condition. The exact action must be unique in the declared original-pixel search region. Local OCR resolves its coordinates, binds a current structural container after recognition, then confirms target pixels and current page/windows again. This avoids binding the first future-page reference to a pre-OCR transition tree. Once bound, container/window changes still stop. Missing labels and movement get bounded read-only recovery: at most four screenshots/eight seconds within the step/plan budget; no input replay. OCR/RPC in flight is not preempted.

Use context_text when selecting a particular item, recipient or object. If the task authorizes the page's unique action regardless of variable display content, its known accessible page guard can supply context; do not require an irrelevant item title. Omitting visual item context is not permission to select an unknown product. Include a meaningful page guard and a previously established search region; do not hide competing actions. Icons or unknown actions still require inspection. Ordinary tap.visual_target and cached visual_query continue to require inspected text plus distinct context.

navigate(...,follow_up={...}) chains the existing bounded timer/returns directly to the final tap acknowledgement. No screenshot/tree observation is inserted before the timer. The final step must be a tap and plan.until/settle_ms must be absent. Navigation has its own budget (up to30s), follow_up timing its own (up to30s); return_back.after may have another bounded navigation budget. Set the client request timeout to cover the complete declared chain, not just one timer. Do not automatically replay a client timeout. One final observation is delivered; inspect navigation and continuation separately, including partial input statuses. Completed navigation can be followed by interrupted timing/returns.

## Prepare before the live segment

For repeated work, load the needed tool signatures and prepare caller-authorized timing, package boundaries, stop conditions and known navigation before opening the first unknown target. Reuse task-owned argument builders in an available persistent runtime; they should return ordinary MCP arguments without connecting another controller, sending input or retrying it. For a short task, reusable in-memory options are enough. No extra per-action preparation call is needed.

Keep observation IDs, element IDs and current coordinates out of reusable defaults. Bind ordinary visual identity from the inspected result. Known future visual selectors may be declared up front under the page/context rules above. A known continuation can finish at the next unknown page; it cannot preselect that page's unseen target. Inspect continuation/navigation and input status before using the new observation. Prepared calls do not resume a partial sequence automatically.

Reuse existing navigate and follow_up/return_back.after to execute known portions locally. Keep business selectors and durations in the task/caller. An unexpected page still needs a decision; a valid next action does not need another observe merely because it came from a template. Measure both the pre-segment preparation and the live interval, so moving preparation earlier is not reported as eliminating it.

For a completely established repeated route, the task caller may chain a small bounded number of ordinary MCP calls in an available persistent runtime, passing each returned latest ID forward. Validate completed navigation/continuation, input status and final foreground before the next call; retain fresh server-side guards for each step. Return immediately on an exception, partial result or unknown state; never replay the whole chain. Show the final result or the first interruption, retaining per-call diagnostics locally. This removes between-call model gaps without adding application loops to the MCP server.
